# 79. XSS

Track: B. Security · Status: proven · Updated: 2026-10-18

## What it is
Cross-site scripting (XSS) is when text from an attacker ends up running as script in someone else's browser: a task title, a comment or a URL that the page inserts as HTML instead of text. The script runs with that user's session, so it can read the page, act as them, or steal tokens. The fix is to put untrusted data into the page only through safe sinks, and to encode for the exact context where it lands:
- **Safe sinks:** `textContent`, `createTextNode`, setting attributes via properties, and templating that auto-escapes.
- **URLs:** check the scheme (`https:` only), since `javascript:` URLs run on click.
- **Unsafe sinks:** `innerHTML`, `insertAdjacentHTML`, `document.write` and inline event handlers. They need sanitized HTML, never raw data.

A Content-Security-Policy (CSP) header is the second layer: it stops injected script from running even if the first layer slips.

## When it is worth it
Always, for any page that shows data that a person or system other than the page's author could have written. That includes run tasks from an intake bot, PR titles, error messages and user agents. Rendering through text sinks costs nothing. A strict CSP is cheap for a small, self-contained page and worth adding as defence in depth. HTML sanitizers (DOMPurify) are only needed when users legitimately submit rich HTML.

## How it fails
- **`innerHTML` with data:** a task containing `<img src=x onerror=...>` is inserted as HTML → the script runs in the operator's browser.
- **Unchecked URL:** a link's `href` comes from data → `javascript:...` runs when clicked.
- **Wrong context:** data is escaped for HTML but placed in an attribute, a `<script>` block or CSS → it breaks out anyway.
- **Server-side templates with autoescape off:** a `|safe` filter or raw string concatenation into HTML → the same injection, rendered on the server.
- **No CSP:** a single slip in any of the above has nothing behind it.

## Review checklist
- [ ] **Does untrusted data reach the page only through text sinks?** · Applies when: the diff renders data from requests, runs, logs, PRs, users or an LLM into HTML. · Block if: that data reaches `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, an inline handler, or an unescaped server template.
- [ ] **Are URLs from data restricted to safe schemes?** · Applies when: the diff sets `href`, `src` or `action` from data. · Block if: the scheme is not checked against an allow-list (`https:`, or relative).
- [ ] **Is data encoded for the context it lands in?** · Applies when: the diff puts data inside an attribute, a `<script>` block, a style, or a URL query. · Block if: it uses HTML-text escaping (or none) in a different context.
- [ ] **Does a new HTML page send a CSP?** · Applies when: the diff adds a route that serves HTML. · Block if: there is no `Content-Security-Policy` restricting `script-src`, and the page shows untrusted data.
