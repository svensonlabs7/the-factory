# 68. IAM

Track: F. Security · Status: proven · Updated: 2026-10-19

## What it is
Identity and Access Management (IAM) governs *who* (a user, service, or workload identity) may do *what* (which actions, on which resources). It has two halves: **authentication** (proving who you are — 069-oauth.md, 070-jwt-rotation.md) and **authorization** (deciding what that identity may do). The defensive foundation is **least privilege**: grant each identity only the permissions its job actually needs, so a compromise is contained to those permissions rather than the whole system. Its companion is **privilege separation** — give each workload its own narrow identity instead of one shared powerful credential — and the related guard against the **confused deputy**, where a privileged component is tricked into acting on an unprivileged caller's behalf. Permissions are expressed as policies (role-based or attribute-based), and the quality of an IAM setup is measured by how small the **blast radius** is when any one credential leaks (proof): the narrower the grant, the less an attacker can do with a stolen token.

## When it is worth it
- Least privilege is worth applying from the very first credential — it costs nothing in function (a scoped token does the job exactly as well as an admin token) and it caps the damage of the compromise that eventually happens (proof). Scoping tokens, separating workload identities, and not sharing one powerful credential are cheap at any scale.
- The *machinery* scales with the org: a full IAM system with roles, groups, policy languages, federation and periodic access reviews is for many humans and services with varied access. For a single-operator system, standing up that apparatus is over-engineering — but the principles (narrowest token, one identity per workload, no standing admin credential where a scoped one works) still apply and are the valuable part.

## How it fails
- **Over-broad permissions:** an identity is granted far more than its job needs (an admin token used for convenience), so a leak of it is catastrophic rather than contained (proof: 7/7 vs 1/7 actions on compromise).
- **Shared credentials:** one powerful token reused across workloads, so a compromise of the least-trusted workload grants the permissions of all of them, and the leak cannot be attributed.
- **Confused deputy:** a privileged component performs an action on behalf of an unprivileged caller without checking the caller was entitled to it (004-reverse-proxies.md, 005-api-gateways.md: "authenticated" is not "authorized").
- **Standing long-lived credentials:** broad, non-expiring tokens that are never rotated, so a past leak stays exploitable indefinitely (070-jwt-rotation.md, 067-secrets-management.md).
- **Privilege creep:** identities accumulate permissions over time and nothing removes the unused ones, so real privilege drifts far above need.
- **No separation of the untrusted workload:** untrusted code runs with a credential that can change production, instead of holding none and handing work to a trusted component.

## Review checklist
- [ ] **Is a new credential scoped to only the actions its workload needs?** · Applies when: the diff introduces or grants a token, key, or role. · Block if: it grants broader permissions than the workload uses (an admin/global token where a scoped one does the job), enlarging the blast radius for no functional gain.
- [ ] **Does each workload have its own identity rather than a shared one?** · Applies when: the diff adds a workload that needs credentials. · Block if: it reuses one powerful shared credential across workloads, so one compromise grants all their access and leaks cannot be attributed.
- [ ] **Does a privileged component verify the caller is authorized, not just authenticated?** · Applies when: the diff has a trusted component act on a request from a less-trusted source. · Block if: it performs the privileged action without checking the caller was entitled to it (confused deputy).
- [ ] **Does untrusted code run without standing privilege?** · Applies when: the diff runs third-party or agent-generated code. · Block if: that code holds a credential that can change production state, rather than holding none and handing the privileged step to a trusted, audited component.

## In the factory
The factory's IAM design is strong, built around privilege separation for its most sensitive boundary:
- **The sandbox holds no GitHub credentials** (`factory/build/run_agent.py:9-10`). The untrusted, agent-generated code can commit only inside its own clone; the *trusted* adapter is the sole holder of the push identity and publishes the branch from a separate checkout (`webhook_adapter.py:339-340`). That is least privilege and privilege separation applied exactly where it matters: a compromised or prompt-injected agent cannot push to the repo, open PRs, or reach GitHub at all (the egress lock, 080-ssrf.md, also blocks it at the network).
- **The sandbox receives only the one secret it needs** — `CLAUDE_CODE_OAUTH_TOKEN`, forwarded explicitly, nothing else (`run_agent.py:42`). Narrowest grant for the job.
- **Requests cannot name an arbitrary target:** the `branch` field is constrained to `^factory/...` (`webhook_adapter.py:183`, 005-api-gateways.md), so even a valid trigger cannot direct work at `main` — a scoping of *what* an authenticated caller may act on.
- **The weaker spots are about authorization-vs-authentication and token scope, already recorded:** the dashboard routes authenticate via Cloudflare Access but do not verify the Access JWT (the JWT Rotation and Reverse Proxies rows — a confused-deputy-shaped risk), and the OAuth/`gh` tokens are long-lived with no documented scope-minimisation or rotation runbook (the OAuth row). No new gap; this card is the IAM framing of those.
- Not applicable at today's load: a role/group system, policy languages, federation, access reviews, per-user permissions. One operator does not need them; the principles above are what carry.

## Proof
`python3 knowledge/systems/proofs/068_iam.py`, comparing the blast radius of a least-privilege vs an over-broad credential for a workload that needs exactly one action:
```
least-privilege token     : does its job=True; if stolen, attacker can do 1/7 actions
over-broad (admin) token  : does its job=True; if stolen, attacker can do 7/7 actions
    beyond its job: ['change branch protection', 'delete repo', 'merge PRs', 'push main', 'read secrets', 'rotate tokens']
```
Both credentials perform the workload's job identically; they differ only in what a *stolen* copy authorises. The least-privilege token confines a compromise to the one action the job needs; the over-broad token hands an attacker everything. Least privilege costs nothing in function and is purely a reduction in blast radius — which is why the factory goes further and gives its untrusted sandbox no push credential at all.
