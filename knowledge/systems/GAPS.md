# Gaps

Places where the factory falls short of a topic card. `/systems-mastery` appends rows; the operator turns them into factory tasks and marks them done.

| Topic | Where | Failure scenario | Severity | Status |
|---|---|---|---|---|
| Timeouts | `.github/workflows/qa-gate.yml:12`, `tests.yml:11`, `static.yml:12`, `static.yml:20` | No job sets `timeout-minutes`, so GitHub's 360-minute default applies. A hung Claude review keeps using runner minutes and plan usage for up to 6 hours, long after the adapter stopped waiting at `CHECKS_TIMEOUT` (20 min) and marked the run `error`. | medium | open |
| Timeouts | `factory/build/run_agent.py:34-35`, `factory/intake/webhook_adapter.py:53` | The comments say the agent's shorter limit lets it end itself. `acp_prompt_timeout` is an idle timeout that every progress event resets: given 40 s, a real run lasted 625 s. Only `AGENT_TIMEOUT` bounds a round. Anyone tuning limits from the comment will trust a deadline that does not exist. | low | open |
| Retries | `factory/intake/webhook_adapter.py:313`, used by `_push` (`:338`) and `_gate_results` (`:354`) | No `git` or `gh` call is retried, not even idempotent reads. Check polling makes up to 160 `gh` calls per gate wait (every 15 s for 20 min, two calls each), so one GitHub 5xx or connection reset ends the run as `error`. During the push it discards the finished build (the workdir is deleted). At PR creation the branch is pushed but no PR opens. During polling the open PR is left unwatched. | medium | open |
| Retries | `.github/workflows/qa-gate.yml:61-66`, `factory/intake/webhook_adapter.py:516-522` | A reviewer whose `claude -p` errors (for example the shared plan token hitting its session limit right after a build) fails its check the same way a BLOCK does. The adapter spends a fix round asking the builder to fix the error text, and after two rounds marks the run `blocked` for code that may be fine. A crashed review needs its check rerun, not a fix round. | medium | open |
| Exponential Backoff | `factory/intake/webhook_adapter.py:232` | `/trigger` answers `429 Too many runs` with no `Retry-After`, although the adapter knows when room returns (a run finishing frees a `MAX_PENDING` slot; the oldest of today's runs ageing past 24 h frees a daily one). Grok Bot, once wired, can only guess when to resend: too soon is rejected again, and too late delays the request. | low | open |
| Idempotency | `factory/intake/webhook_adapter.py:588-613` | `/trigger` takes no idempotency key. A client that lost the response and retries (new timestamp, so a new signature) creates a second run: a duplicate build, a duplicate PR and twice the plan usage (proven against the adapter: one task, two run ids). An exact resend gets `401 Replayed request`, so the client cannot learn the run id it created. | medium | open |
| Idempotency | `factory/intake/webhook_adapter.py:715-732`, `:432` | `_recover` marks in-flight runs `error` but stops nothing. The agent runs in its own session (`start_new_session=True`), so if the adapter dies mid-round, the agent and its container keep running unsupervised until they end on their own, spending plan usage on work that is then discarded. Reasoned from POSIX process semantics, not run. | medium | open |
| Backpressure | `HEARTBEAT.template.md:15,18`, `factory/intake/webhook_adapter.py` (no writer) | `intake_queue_depth` and `last_pr_merged` are in the HEARTBEAT table, but nothing ever writes them, so `/heartbeat` always reports a queue depth of 0 and no merges. Grok Bot, the intended watcher, would read a full queue as empty. The dashboard's live `pending` count is correct. | low | open |
| Dead Letter Queues | `factory/intake/webhook_adapter.py:397-414` (`_finish`) | HEARTBEAT reports only the latest run. A run that ends `failed`, `error`, `blocked` or `timeout` sets `pipeline_status`, and the next run that completes resets it to `idle` with `blocking_reason` "—" (proven against the adapter). The dead run stays on disk, but no count of unresolved dead runs exists and nothing alerts on one, so a requested feature that never shipped can go unnoticed. | medium | open |
| Webhooks | `factory/intake/webhook_adapter.py:181` (`TriggerPayload.task`) | `task` has no length limit and the body no size cap. A 2 MB task is accepted with 202, cloned for, then fails at spawn with `[Errno 7] Argument list too long`, because the prompt is passed as an argument and macOS `ARG_MAX` is 1 MB (proven against the adapter). The caller learns of it only by polling, and the error does not say "task too long". A `max_length` on the field returns 422 at the door. | low | open |
| Health Checks | `factory/intake/webhook_adapter.py:627-629` (`/health`) | `/health` is liveness only. Nothing reports whether the factory can deliver: Docker and Colima, the egress proxy, `gh` auth, the Claude token, free disk. With `gh` logged out, `/health` stayed `ok` while a run built, pushed and then failed at PR creation (proven against the adapter). Every queued run would do the same, spending plan usage on work that cannot ship. | medium | open |
| Health Checks | `factory/intake/webhook_adapter.py:627-629`, `:84`, `:536` | `/health` does not report the running commit, so a merge that was never followed by a restart leaves stale code serving unnoticed. On 2026-10-18 only comparing the process start time with the merge time showed that #56 was live. Separately, the comments at `:84` and `:536` say `the-machine` polls HEARTBEAT, but the factory shares nothing with `the-machine` and Grok Bot is the intended watcher. | low | open |
| Secrets Management | `factory/intake/webhook_adapter.py:338-350` (`_push`) | The sandboxed agent holds `CLAUDE_CODE_OAUTH_TOKEN`, and the egress lock-down covers its network but not its commits, which the adapter pushes with no secret scan. The repo is public, so a token the agent writes into a commit (debug output, a test fixture, a prompt-injected task) is published at once. gitleaks in CI then fails the check, but too late: the token must be revoked. Proven with a fake key against the adapter: the run completed and origin held it. `gitleaks` is installed on the host, so `_push` could scan `since..head` before `git push` and fail the run. | high | open |
| SSRF | `factory/build/egress.sh:23-30` | The firewall rules sit in `DOCKER-USER`, which filters only forwarded traffic. Traffic from the sandbox subnet to the Colima VM itself is never checked, and a sandbox container opened `172.30.0.1:22` (the VM's `sshd`). The internet and the Mac stayed blocked. `sshd` is key-only, so this is attack surface, not an open door, but an `sshd` flaw would give a compromised agent the VM, which has the Mac's home directory (and `.env`) mounted. An `INPUT` rule dropping new connections from `172.30.0.0/24` closes it, and egress.sh's proof step should test it. | medium | open |
| SQL Injection (CI expression injection) | `.github/workflows/qa-gate.yml:49,61` | `${{ github.base_ref }}` is pasted into `run:` scripts in the privileged `pull_request_target` job that holds `CLAUDE_CODE_OAUTH_TOKEN`. Git accepts a branch named `main$(touch${IFS}pwned)`, and with GitHub's text substitution emulated, bash ran the command. Creating such a base branch needs push access, which already allows a secret-bearing `pull_request` workflow, so the gain to an attacker is small. GitHub's hardening guide still says to pass it as `env: BASE_REF: ${{ github.base_ref }}` and use `"$BASE_REF"`. | low | open |
| XSS | `factory/intake/webhook_adapter.py` (`/command` route), `factory/intake/command.html` | The dashboard is XSS-safe by construction: hostile run data rendered as text in the browser, and nothing ran. But `/command` sends no `Content-Security-Policy`, `X-Content-Type-Options: nosniff` or `frame-ancestors`, so one future `innerHTML` slip has nothing behind it, and the factory builds UI itself. A strict CSP with a hash for the one inline script, plus `frame-ancestors 'none'`, adds the second layer. | low | open |
| CORS | `factory/intake/webhook_adapter.py:173` (`app`) | The adapter accepts any `Host` header (`Host: rebind.attacker.example` returned 200). Binding to `127.0.0.1` and sending no CORS stops other sites from reading it, which the browser test confirmed, but not DNS rebinding: a page whose domain re-resolves to `127.0.0.1` is same-origin with `localhost:7654` and can read `/command/data` (run tasks, PRs, heartbeat), `/heartbeat` and `/status` from the operator's browser. Writes still need the HMAC secret. `TrustedHostMiddleware` limited to `localhost`, `127.0.0.1` and the two tunnel hostnames closes it. | low | open |
| OAuth | `factory/intake/README.md` (rotation section covers only the webhook secret) | The Claude Code OAuth token lives in `.env` and in the repo's Actions secrets, and the `gh` OAuth token lives in the host keychain. Both are long-lived bearer tokens, and no runbook says where each is stored or how to revoke and replace it. After a leak (see the Secrets Management row), every minute spent finding the copies is a minute the token stays live. A short runbook (revoke at the provider, issue a new token, update `.env` and the Actions secret, restart the adapter) closes it. | low | open |
| JWT Rotation | `factory/intake/webhook_adapter.py` (dashboard routes `/command`, `/command/data`) | Cloudflare Access adds a signed `Cf-Access-Jwt-Assertion` header to every request it allows, and Cloudflare's guidance is for origins to validate it (signature by `kid` from the team's certs endpoint, then `aud` and `iss`). The adapter does not, so it cannot tell a request that passed Access from one that reached `localhost:7654` another way, such as a local process or the DNS-rebinding page in the CORS row. Validating it on the dashboard routes would close that, at the cost of fetching and caching the certs as keys rotate (about every 6 weeks). The intake route already requires its own HMAC. | low | open |
| TLS | Cloudflare zone `svensonlabs.dev` (edge settings, not in the repo) | Both `factory.svensonlabs.dev` and `dash.svensonlabs.dev` still negotiate TLS 1.0 and 1.1 (`ECDHE-ECDSA-AES128-SHA`), which RFC 9325 says MUST NOT be negotiated, and neither sends `Strict-Transport-Security`. The only clients are Grok Bot and the operator's browser, so nothing needs the old versions. Fix in Cloudflare: Minimum TLS Version 1.2, and HSTS on (at least for `dash`, which browsers use). Proven with Python `ssl` pinned to each version. | low | open |
| Logging | `factory/intake/com.svenson.factory-intake.plist:40-43`, `factory/intake/webhook_adapter.py:78,90` | uvicorn's own lines, including every access-log line in `intake.out.log`, carry no timestamp (0 of 5,874 lines), so "when did this `/trigger` arrive?" cannot be answered from the access log. Nothing rotates `intake.out.log` or `intake.err.log`: the dashboard's 15 s poll alone adds about 500 KB a day (about 180 MB a year). `rejected.jsonl` stops growing at 5 MB by dropping new entries, losing the newest evidence first. Fixes: pass uvicorn a log config with `%(asctime)s`, rotate the files (a `newsyslog.d` entry, or a size-based rotating handler), and rotate `rejected.jsonl` instead of capping it. | low | open |
| Metrics | `factory/intake/webhook_adapter.py:479-492` (`_build_round`) | A Claude plan usage-limit pause, the factory's most constrained resource, writes no action-log event. It only overwrites HEARTBEAT's `pipeline_status`, which the next run resets, and then sleeps. So "how often does the plan throttle us, and for how long?" cannot be answered. Grepping run logs for the message gave 3 runs where only 1 was real (the others were test code and a task about the feature). One `_log_action(run_id, "paused", wait=..., resume=...)` makes it countable. | low | open |
| Monitoring | `infra/cloudflare-tunnel/config.yml:6`, `factory/intake/webhook_adapter.py` (`/heartbeat`) | Nothing outside the Mac watches the factory. The access log shows only local and the operator's own clients (the dashboard). `/heartbeat` is not routed through the tunnel, so Grok Bot, the intended watcher, cannot reach it. A probe without credentials gets Cloudflare Access's identical 401 for `/health` and for a path that does not exist, so it proves only that Cloudflare is up. If the adapter, tunnel or Mac goes down, nobody knows until a trigger fails. Needs: route `/heartbeat` for Grok Bot (behind the existing Access service token), and have it alert when `alive_at` goes stale or the authenticated `/health` probe fails. | medium | open |
| SLIs | `factory/intake/webhook_adapter.py` (`_finish`, run `meta.json`) | The factory's only success signal is `status == "completed"` (the gate passed), and it disagrees with what shipped in both directions. No outcome SLI is defined, and the PR's fate is never recorded, so "how often does the factory deliver on its own?" (5/8) needs a manual `gh` lookup. | Error Budgets | `.github/workflows/qa-gate.yml`, `tests/test_adapter.py` (fake agent, fake Docker) | The gate checks code quality and fake-backed tests, so a change to real sandbox or infra behaviour can pass every check and still not work. | Observability | `factory/build/run_agent.py` (ACP agent), run logs `.factory-logs/<run_id>.log` | How much Claude plan usage a run consumes cannot be observed: every `Tokens:` line in every run log reports `input (total 0)` and `output (total 0)` (32 lines across 8 runs), because the agent integration passes no usage back. | Race Conditions | `factory/intake/webhook_adapter.py:338-350` (`_push`), `:50` (`FACTORY_ROOT` default) | `_push` runs `git fetch <agent clone> <branch>` and then reads `FETCH_HEAD` in `FACTORY_ROOT`. The live plist does not set `FACTORY_ROOT`, so that is the operator's own working copy, `/Users/labs/projects/the-factory`. Any other `git fetch` there in that window (the operator, an editor's auto-fetch) rewrites `FETCH_HEAD`, and the adapter pushes someone else's commit to the run's branch. Reproduced in scratch repos. Fix: fetch into a ref the run owns (`<branch>:refs/factory/<run_id>`) and read that, and give the adapter its own clone instead of the operator's checkout. | medium | open |
| CI/CD | `.github/workflows/tests.yml:15`, `factory/intake/com.svenson.factory-intake.plist:9-16` | Neither CI nor the adapter pins anything. CI installs the newest `fastapi` (and friends) on the runner's Python 3.12; the adapter runs `uv run --with fastapi --with uvicorn --with python-dotenv` on Python 3.11.15. On 2026-10-18 the live adapter ran FastAPI 0.144.0, the last `tests` run installed 0.145.0, and a fresh resolve gave 0.146.0, so production runs a version CI never tested. A FastAPI or Starlette release can break the adapter on its next fresh environment (a uv cache clean or upgrade) with no code change, and the crash-looping adapter takes intake down. Fix: one lockfile (`pyproject.toml` + `uv.lock`) used by both CI (`uv sync --frozen`) and the plist, with the Python version pinned. | medium | open |
| Rollbacks | `.github/workflows/qa-gate.yml:3-5` (`pull_request_target`), branch protection on `main` (`enforce_admins: true`), `factory/qa/README.md` | The gate cannot roll itself back. `pull_request_target` runs main's copy of the workflow and the review skills, so a merged change that breaks the gate (the workflow, a skill, the pinned `claude` CLI) also reviews its own revert. The revert's required checks fail or never report, and `enforce_admins` stops even the admin from merging. Every PR, the fix included, is stuck until the operator edits branch protection by hand, and no break-glass procedure is written down. Fix: document the steps in `factory/qa/README.md` (lift `enforce_admins`, merge the revert, restore protection, note it in HEARTBEAT incidents). | medium | open |
| Rollbacks | `factory/intake/webhook_adapter.py:732` (`_recover()` at import), `:102` (`_load`) | One unparseable `.meta.json` (a format a newer version wrote before a rollback, or a hand edit) makes `json.loads` raise during import, so the adapter never starts and launchd's `KeepAlive` restarts it into the same crash; intake is down until someone finds and moves the file.
