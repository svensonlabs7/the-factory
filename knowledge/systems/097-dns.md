# 97. DNS

Track: J. Networking · Status: proven · Updated: 2026-10-19

## What it is
DNS is the internet's name-to-address lookup. A resolver walks from the root to the zone's authoritative servers and gets back records (an `A`/`AAAA` address, a `CNAME` alias, an `MX`, …), each carrying a TTL. RFC 1034 says the TTL "describes how long a RR can be cached before it should be discarded"; it "is assigned by the administrator for the zone where the data originates". Resolvers cache answers for the TTL so most lookups are local and fast. RFC 2308 adds *negative* caching: a "this name does not exist" (NXDOMAIN) or "no record of this type" (NODATA) answer is also cached, for a TTL taken from "the minimum of the MINIMUM field of the SOA record and the TTL of the SOA itself". So both the presence and the absence of a name are cached, and a change is invisible to a resolver until the cached entry expires.

## When it is worth it
You do not choose to use DNS; every outbound call by name depends on it. The decisions are operational:
- **TTL**: low TTL means faster change and more query traffic; high TTL means fewer queries and a longer stale window. RFC 1034's rule: lower the TTL well before a planned change, flip, then raise it again.
- **Where to resolve**: a managed DNS provider (Cloudflare, Route 53) versus running your own. For one host with a handful of names, a managed zone is right; running `bind`/`unbound` is over-engineering until you need split-horizon, internal zones, or query-level policy.
- **Health-checked / failover DNS and GeoDNS** matter only once you have multiple origins or regions to steer between (085-failover.md, 086-multi-region-deployment.md).

## How it fails
- **Negative cache outlasts the fix:** a lookup for a name created moments later is cached as NXDOMAIN for the zone's negative TTL, so the new name stays unresolvable for up to that long even though it now exists (proof A).
- **Stale positive cache after a cutover:** an `A` record is flipped, but resolvers keep handing out the old IP until the TTL expires, so clients hit the dead origin for up to TTL seconds (proof B).
- **DNS is a hard dependency and a SPOF:** if resolution fails, every call by name fails even when the target IP is healthy; a resolver outage looks like a total outage.
- **Unfiltered DNS as an egress channel:** a network that blocks or proxies connections but lets DNS queries out leaves an out-of-band path — a lookup of `secret.attacker.example` reaches the attacker's authoritative server regardless of the connection allowlist (the DNS row in GAPS.md).
- **ndots and search-domain surprises:** a high `ndots` or a search list turns a bare name into several failed lookups before the real one, adding latency and load.
- **TTL ignored by an intermediary:** a load balancer or client that resolves once at startup and never again pins itself to an IP that later moves.

## Review checklist
- [ ] **Is a name's record changed without first lowering its TTL?** · Applies when: the diff changes an `A`/`AAAA`/`CNAME` for a name clients are actively using. · Block if: the cutover expects an immediate switch but the current TTL is long and was not lowered ahead of time, so clients hit the old target for up to the TTL.
- [ ] **Does new egress depend on DNS that the network policy allows but does not scope?** · Applies when: the diff adds outbound calls from a sandbox or restricted network, or changes its resolver/egress rules. · Block if: arbitrary DNS lookups can leave while connections are allowlisted, so DNS is an unmonitored side channel.
- [ ] **Is resolution failure handled distinctly from connection failure?** · Applies when: the diff adds a client that calls a remote host by name on a path where an outage must degrade gracefully. · Block if: a resolver failure is treated as a permanent error (or retried with no backoff), rather than a transient the caller can survive (011-timeouts.md, 012-retries.md).
- [ ] **Is a long or zero DNS TTL chosen deliberately?** · Applies when: the diff sets or changes a record's TTL. · Block if: the value is picked with no statement of the change-speed vs. query-load trade-off, or a zero TTL is used where no fast cutover is needed.

## In the factory
- The `svensonlabs.dev` zone is on Cloudflare (`SOA bristol.ns.cloudflare.com … 1800`, measured). `factory.svensonlabs.dev` and `dash.svensonlabs.dev` both resolve to Cloudflare's anycast front (`104.21.45.110`, `172.67.213.143`) at **TTL 300**; the real origin is the `cloudflared` tunnel (`infra/cloudflare-tunnel/config.yml:1`), so the public `A` records never need to change when the host does. Right: the tunnel removes the DNS-cutover problem for the factory's own names.
- The factory depends on DNS it does not own: `api.anthropic.com`, `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org` (`factory/build/egress/allow`) and `api.github.com` (measured TTL 50) for `gh`. A resolver outage would fail builds exactly like a network outage; at one host with retries, this is an accepted risk, not a thing to engineer around.
- A warm DNS lookup is cheap here: `factory.svensonlabs.dev` measured at ~1.0 ms (091-latency.md), paid once per pooled connection (028-connection-pooling.md).
- **Gap:** the sandbox egress lock drops direct connections and allowlists the rest at the proxy by hostname (`factory/build/egress.sh`, `egress/allow`), but DNS is **not** filtered. A container on `factory-sandbox` resolved `example.com` and a never-seen `probe-<ts>.svensonlabs.dev` (which reached Cloudflare's authoritative servers and returned the zone SOA) while a direct HTTPS `GET` timed out. So a compromised or injected agent has an out-of-band channel the hostname allowlist and the CI secret scan never see. Added to GAPS.md.
- Not applicable at today's load: GeoDNS, health-checked failover DNS, split-horizon/internal zones, running our own resolver.

## Proof
`python3 knowledge/systems/proofs/097_dns.py`, a deterministic resolver-cache model (RFC 1034 positive TTL, RFC 2308 negative caching) driven by the TTLs measured with `dig` against the live zone (A 300 s, SOA MINIMUM 1800 s):
```
A  name created at t=60 s; negative TTL 1800 s -> first resolves at t=1800 s (29 min of failure after it existed)
A  lower SOA MINIMUM to 60 s first      -> first resolves at t=60 s (fix)
B  flip A record with TTL 300 s  -> clients see new IP after 200 s of stale answers
B  drop TTL to 30 s before the flip -> stale window 0 s (RFC 1034: lower TTL ahead of a change)
```
The unfiltered-DNS finding is from live probes: `docker run --network factory-sandbox … nslookup` resolved `example.com` and a fresh `probe-<ts>.svensonlabs.dev`, while `curl -m 5 https://example.com` from the same network returned code 000 (timeout). Measured TTLs: `dig +ttlid factory.svensonlabs.dev A` → 300; `dig api.github.com A` → 50; `dig svensonlabs.dev SOA` → negative TTL 1800.
