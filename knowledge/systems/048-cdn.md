# 48. CDN

Track: I. Performance and scaling · Status: proven · Updated: 2026-10-19

## What it is
A content delivery network is a fleet of edge servers (points of presence, POPs) near users that terminate connections and serve cached copies of content, fetching from the origin on a miss. It cuts latency, because the round trip is to a nearby POP, and offloads the origin. Modern CDNs also act as the front door: TLS, DDoS absorption, a WAF, access control and tunnels to private origins.

What gets cached is a policy, and getting it wrong is the main risk:
- Cloudflare caches by file extension. "The Cloudflare CDN does not cache HTML or JSON by default".
- It does not cache a response marked `private`, `no-store`, `no-cache` or `max-age=0`, or one that sets a cookie.
- Responses with no `Cache-Control` are still cached for some status codes (200 for 120 minutes, 404 for 3 minutes) when the extension is cacheable.

Web cache deception exploits this. When an origin serves a private page at a static-looking path (`/account/foo.jpg` treated as `/account`), the CDN caches the private response and serves it to an attacker. Cloudflare's Cache Deception Armor refuses to cache when the extension does not match the `Content-Type`.

## When it is worth it
A CDN is worth it for any public site or API with users far from the origin, static assets, large downloads, or exposure to attack traffic. As a cache it pays off for content requested often per POP: one hot asset is offloaded almost entirely, while a long tail of rarely requested objects mostly misses (proof). As a front door (TLS, WAF, access), it is worth it even for tiny private services. Tuning edge caching for authenticated, per-user or real-time content is the over-engineering case: keep it uncached.

## How it fails
- **Private content cached:** a per-user or authenticated response without `private` or `no-store` is cached at the edge and served to others, often after someone adds a "cache everything" rule.
- **Web cache deception:** the origin serves a private page for `/page/anything.css`, and the CDN caches it under the static-looking path.
- **Long-tail misses:** many distinct objects, each rarely requested per POP → a low hit ratio and little offload (proof B), unless tiered caching or a longer TTL is used.
- **Stale after deploy:** long TTLs on unversioned asset names (`app.js`) keep the old version at the edge, and purges are missed or slow. Use content-hashed file names.
- **Cache key too broad or too narrow:** ignoring a header or query parameter the response varies on serves the wrong variant; including noise such as tracking parameters destroys the hit ratio.
- **Origin exposed:** the origin is reachable directly, bypassing the CDN's WAF and access control.

## Review checklist
- [ ] **Are authenticated and per-user responses uncacheable at the edge?** · Applies when: the diff adds or changes a route served through a CDN that returns per-user, authenticated or session data. · Block if: the response lacks `Cache-Control: private` or `no-store`, or a cache rule could store it.
- [ ] **Can a static-looking path return dynamic or private content?** · Applies when: the diff adds routing, catch-all routes or path normalisation behind a CDN. · Block if: a request like `/private/x.css` returns the private page with a 200, instead of a 404 or a content type that matches the extension.
- [ ] **Are cached assets versioned?** · Applies when: the diff serves static assets with long TTLs. · Block if: file names are not content-hashed and there is no purge on deploy.
- [ ] **Does the cache key match what the response varies on?** · Applies when: the diff configures cache keys, or a response that varies by header, cookie or query. · Block if: a varying input is missing from the key (or from `Vary`), or noise inputs are in it.
- [ ] **Is the origin reachable only through the CDN?** · Applies when: the diff exposes an origin behind a CDN or proxy. · Block if: the origin also accepts direct traffic that skips the CDN's TLS, WAF or access control.

## In the factory
- Cloudflare is the factory's CDN, used as a front door, not as a cache. Both hostnames are reached only through a Cloudflare Tunnel to `localhost:7654` (`infra/cloudflare-tunnel/config.yml`). The adapter binds `127.0.0.1` and has no public origin, and Cloudflare Access guards both hostnames.
  - Live edge responses carry `server: cloudflare` and a `cf-ray` ending in `-EWR` (the Newark POP).
  - Access's own responses (the 401 on `factory`, the login redirect on `dash`) send `Cache-Control: private, max-age=0, no-store, no-cache`.
  - Nothing is cached, which is right for an authenticated dashboard and a webhook.
- The factory is not exposed to web cache deception. The tunnel's ingress matches exact paths only (`^/(command(/data)?)?$`), so `/command/data.css`, `/command/data/x.css` and `/health.css` all get the tunnel's 404 (`cloudflared tunnel ingress rule`). Right.
- The adapter's own responses send no `Cache-Control`. JSON and HTML are not cached by default, so this is safe today. Adding `no-store` would keep it safe under a future cache rule (002-caching.md).
- Not applicable at today's load: edge caching, tiered cache, purges and asset versioning. There are no public static assets.
